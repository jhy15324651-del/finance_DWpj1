## 🎞 Slide 3. 핵심 기능 3가지

### 슬라이드 내용
```
1️⃣ OCR 포트폴리오 인식
   - 증권사 앱 스크린샷 → 자동 종목 추출
   - Tesseract OCR + 증권사별 전처리
   - 한글 종목명 → 영문 티커 자동 변환 (500+ 종목)

   - 코사인 유사도 알고리즘으로 TOP 3 매칭
   - 투자 철학, 장단점, 개선 제안 제공

### 발표 대본
"이 프로젝트의 핵심 기능은 크게 3가지입니다.

첫 번째, OCR 포트폴리오 인식입니다. 사용자가 토스나 미래에셋 같은 증권사 앱에서 스크린샷을 찍으면, 제 서비스가 Tesseract OCR을 사용해서 종목명과 비중을 자동으로 읽어냅니다. 여기서 재미있는 점은, 증권사마다 화면 레이아웃이 다르기 때문에 각 증권사별로 이미지 전처리 방식을 다르게 적용했다는 겁니다. 예를 들어 토스는 파란 배경을 먼저 제거해야 인식률이 올라가더라구요. 또한 '삼성전자'를 인식하면 자동으로 미국 주식 티커인 'SSNLF'로 변환합니다. 500개 이상의 종목 매핑 테이블을 직접 구축했습니다.

두 번째, 투자대가와의 포트폴리오 비교입니다. 워렌 버핏, 캐시 우드 같은 유명 투자자들은 SEC에 분기마다 13F 보고서를 제출합니다. 저는 이 데이터를 자동으로 수집하는 시스템을 만들었어요. 그리고 사용자 포트폴리오와 투자대가들의 포트폴리오를 코사인 유사도 알고리즘으로 비교해서, 가장 비슷한 TOP 3를 찾아줍니다. 단순히 겹치는 종목 개수만 세는 게 아니라, 각 종목의 비중까지 고려합니다.

세 번째, AI 맞춤형 포트폴리오 추천입니다. TOP 3 투자자가 나왔으니, 이제 '그래서 나는 뭘 사야 하는데?'라는 질문에 답해야겠죠. 저는 OpenAI GPT-4에게 4명의 투자자가 회의실에 모여 토론한 후 합의한 포트폴리오를 만들어달라고 요청합니다. 단순히 25%씩 평균 내는 게 아니라, 4명 모두가 동의할 만한 종목을 선정하도록 프롬프트를 설계했습니다. 비용 절감을 위해 Gemini로도 전환 가능하게 만들었어요."

## 🎞 Slide 6. 가장 어려웠던 기술적 문제 (1) - OCR 인식률 향상

### 슬라이드 내용
```
문제 상황
- 초기 OCR 인식률: 약 60%
- 특히 토스 앱 스크린샷 인식 실패율 높음
- 원인: 파란 배경, 작은 글씨, 그림자 효과

시도한 방법
1️⃣ Tesseract 파라미터 튜닝 → 70%로 향상
2️⃣ 이미지 전처리 (그레이스케일, 대비 증가) → 75%로 향상
3️⃣ 증권사별 전처리 전략 분리 → 85%로 향상

최종 해결책
- 전략 패턴 (Strategy Pattern) 적용
- TossPreprocessor: 파란 배경 제거 + 적응형 임계처리
- DefaultPreprocessor: 기본 그레이스케일 변환
- OcrService가 증권사 타입에 따라 적절한 전처리기 선택

결과
- 최종 인식률: 85~90%
- 새 증권사 추가 시 코드 수정 최소화
```

### 발표 대본
"개발 중 가장 어려웠던 문제 중 하나는 OCR 인식률 향상이었습니다. 처음에는 스크린샷을 그냥 Tesseract에 넣었더니 인식률이 60%밖에 안 나왔어요. 특히 토스 앱은 파란 배경 때문에 거의 인식이 안 됐습니다.

먼저 Tesseract 파라미터를 조정해봤어요. Page Segmentation Mode를 바꾸고, OCR Engine Mode를 LSTM으로 변경했더니 70%까지 올라갔습니다. 그 다음엔 이미지 전처리를 추가했어요. 그레이스케일로 변환하고 대비를 높였더니 75%까지 올라갔고요.

하지만 여전히 토스는 문제였습니다. 그래서 증권사별로 전처리 방식을 다르게 적용하는 전략 패턴을 도입했어요. 토스는 먼저 파란 배경을 제거하고, 적응형 임계처리로 글씨를 선명하게 만들었습니다. OpenCV 라이브러리를 사용해서 HSV 색공간에서 파란색 범위를 마스킹하는 방식으로 구현했어요.

최종적으로 인식률이 85~90%까지 올라갔고, 새로운 증권사를 추가할 때도 기존 코드를 건드리지 않고 새 전처리기 클래스만 추가하면 되도록 설계했습니다. 이 경험으로 확장 가능한 설계의 중요성을 배웠습니다."

## 🎞 Slide 7. 가장 어려웠던 기술적 문제 (2) - SEC API Rate Limit 대응

### 슬라이드 내용
```
문제 상황
- SEC API 제한: 초당 10회
- 8명의 투자자 × 평균 3회 API 호출 = 24회
- 초과 시 429 Too Many Requests + IP 차단 위험

시도한 방법
1️⃣ Thread.sleep() 사용 → 부정확, 누적 오차 발생
2️⃣ ScheduledExecutorService → 복잡도 증가
3️⃣ Guava RateLimiter → 정확하고 간단!

최종 해결책
```java
private final RateLimiter rateLimiter = RateLimiter.create(9.0);

rateLimiter.acquire();  // 자동 대기
httpClient.newCall(request).execute();
```

추가 기능
- Exponential Backoff 재시도 (2초 → 4초 → 8초)
- Checkpoint 기반 Resume (서버 재시작 시 중복 수집 방지)

결과
- 8명 수집 완료 시간: 약 2분 30초
- API 제한 위반 0건
- 서버 재시작 후에도 진행 상황 유지
```

### 발표 대본
"두 번째로 어려웠던 문제는 SEC API의 Rate Limit 대응이었습니다. SEC는 공식적으로 초당 10회 제한을 두고 있고, 이를 초과하면 IP가 차단될 수 있어요. 8명의 투자자 데이터를 수집하려면 평균 24번 정도 API를 호출해야 하는데, 그냥 반복문을 돌리면 순식간에 제한을 초과하게 됩니다.

처음엔 Thread.sleep()으로 100ms씩 대기했는데, 이게 누적 오차가 생기더라구요. 1초에 10번이 아니라 11번 호출되는 식으로요. 그래서 더 정밀한 방법을 찾다가 Guava 라이브러리의 RateLimiter를 발견했습니다.

RateLimiter는 초당 정확히 9회로 제한할 수 있고, acquire() 메서드를 호출하면 자동으로 대기해줍니다. 안전 마진을 위해 10회가 아닌 9회로 설정했어요. 또한 네트워크 오류나 타임아웃이 발생하면 Exponential Backoff 방식으로 재시도합니다. 2초, 4초, 8초 이렇게 대기 시간을 늘려가면서 최대 3번까지 재시도하도록 했습니다.

추가로 Checkpoint 시스템을 도입해서, 서버가 재시작되더라도 이미 수집 완료한 투자자는 건너뛰고 이어서 진행할 수 있게 만들었어요. 최종적으로 8명의 데이터를 약 2분 30초 만에 안정적으로 수집할 수 있게 됐습니다."

## 🎞 Slide 8. 가장 어려웠던 기술적 문제 (3) - AI 프롬프트 엔지니어링

### 슬라이드 내용
```
문제 상황
- AI가 일관된 JSON 형식으로 응답하지 않음
- 종목 개수가 10개가 아닌 7개만 반환
- 비중 합계가 100%가 아님 (98.5%, 103% 등)
- 마크다운 코드 블록 (```json```) 포함

시도한 방법
1️⃣ 프롬프트에 "JSON만 출력" 명시 → 여전히 마크다운 포함
2️⃣ temperature 낮춤 (0.8 → 0.3) → 일관성 향상
3️⃣ 예시 JSON 제공 → 형식 준수율 향상
4️⃣ 검증 로직 추가 → 비중 합계 체크

최종 해결책
- System Prompt: "순수 JSON만 출력하세요"
- User Prompt: 상세한 JSON 스키마 + 필수 조건
- 후처리: 마크다운 제거 + 비중 합계 검증
- 실패 시 재시도 (최대 3회)

결과
- JSON 파싱 성공률: 95% 이상
- Gemini 2.0이 GPT-4보다 더 일관적
```

### 발표 대본
"세 번째 어려운 문제는 AI 프롬프트 엔지니어링이었습니다. 제가 AI에게 포트폴리오를 JSON 형식으로 만들어달라고 요청했는데, 처음엔 마크다운 코드 블록으로 감싸서 반환하거나, 종목 개수가 10개가 아닌 7개만 나오거나, 비중 합계가 100%가 아닌 경우가 많았어요.

여러 가지 방법을 시도했습니다. 먼저 프롬프트에 '반드시 JSON만 출력하세요'라고 명시했는데도 여전히 마크다운이 붙더라구요. 그래서 temperature를 0.8에서 0.3으로 낮췄더니 일관성이 크게 향상됐습니다. temperature가 낮을수록 AI가 더 결정론적으로 답변하거든요.

또한 프롬프트에 예시 JSON을 직접 보여주고, '종목은 정확히 10개, 비중 합계는 100%'라는 필수 조건을 강조했습니다. 그리고 응답을 받은 후에는 마크다운 코드 블록을 제거하고, 비중 합계가 100%인지 검증하는 로직을 추가했어요. 만약 검증에 실패하면 최대 3번까지 재시도합니다.

재미있는 발견은, Gemini 2.0이 GPT-4보다 오히려 더 일관된 JSON을 생성한다는 점이었습니다. 최종적으로 JSON 파싱 성공률이 95% 이상으로 올라갔고, 실패한 경우에도 재시도로 해결할 수 있게 됐습니다."

## 🎞 Slide 9. 보안 설계

### 슬라이드 내용
```
적용한 보안 기술

1️⃣ Spring Security + RBAC
   - 역할 기반 접근 제어 (USER, ADMIN)
   - 관리자 페이지는 ROLE_ADMIN만 접근

   - 삭제된 데이터 복구 가능

```

### 발표 대본
"금융 플랫폼이다 보니 보안에 특히 신경을 많이 썼습니다. 첫 번째로 Spring Security를 도입해서 역할 기반 접근 제어를 구현했어요. 일반 사용자는 자기 포트폴리오만 볼 수 있고, 관리자는 모든 콘텐츠를 관리할 수 있습니다.

비밀번호는 절대 평문으로 저장하지 않습니다. BCrypt 알고리즘으로 암호화하는데, 이게 재미있는 게 같은 비밀번호를 입력해도 매번 다른 해시값이 나와요. Salt라는 랜덤 값을 자동으로 추가하기 때문입니다. 그리고 복호화가 불가능한 일방향 해시라서, DB가 해킹당해도 원본 비밀번호는 알 수 없습니다.

SQL Injection 공격은 JPA를 사용하면 자동으로 방어됩니다. JPA가 내부적으로 Prepared Statement를 사용하거든요. 직접 SQL 문자열을 연결하는 방식은 프로젝트 전체에서 사용하지 않았습니다.

마지막으로 Soft Delete와 감사 로그를 도입했습니다. 관리자가 부적절한 게시글을 삭제할 때, 실제로 DB에서 지우는 게 아니라 'is_deleted = true' 플래그만 변경해요. 그리고 누가, 언제, 왜 삭제했는지 감사 로그에 기록합니다. 법적 분쟁이나 규제 요구 시 추적 가능성을 확보한 거죠."

## 🎞 Slide 10. 성능 최적화

### 슬라이드 내용
```
적용한 최적화 기법

1️⃣ ThreadLocal Tesseract
   문제: Tesseract는 Thread-Safe하지 않음
   해결: 각 스레드마다 별도 인스턴스 생성
   결과: 10명 동시 업로드 시 오류 없이 처리

2️⃣ Stock Quote 캐시 (15분 TTL)
   문제: 100명이 AAPL 시세 조회 → API 100회 호출
   해결: DB 캐시 테이블에 15분간 저장
   결과: API 호출 99% 감소 (100회 → 1회)

3️⃣ LAZY 로딩 + Fetch Join
   문제: EAGER 로딩 시 N+1 문제 발생
   해결: 기본 LAZY + 필요시 Fetch Join
   결과: 불필요한 쿼리 제거

4️⃣ RateLimiter (SEC API)
   문제: API 제한 초과 시 IP 차단
   해결: Guava RateLimiter로 초당 9회 제한
   결과: API 제한 위반 0건
```

### 발표 대본
"성능 최적화도 여러 방법으로 적용했습니다. 첫 번째는 ThreadLocal Tesseract입니다. Tesseract는 원래 Thread-Safe하지 않아서 동시에 여러 사용자가 이미지를 업로드하면 오류가 나요. 그래서 ThreadLocal을 사용해서 각 스레드마다 독립적인 Tesseract 인스턴스를 만들었습니다. 이렇게 하니까 10명이 동시에 업로드해도 문제없이 처리됩니다.

두 번째는 주식 시세 캐시입니다. Yahoo Finance API를 사용하는데, 100명이 애플 주식 시세를 조회하면 100번 API를 호출하게 되잖아요. 그래서 DB에 캐시 테이블을 만들고 15분간 저장하도록 했습니다. 이렇게 하니까 API 호출이 99% 감소했어요.

세 번째는 JPA의 LAZY 로딩입니다. 연관 엔티티를 항상 조회하면 N+1 문제가 발생할 수 있어서, 기본적으로는 LAZY 로딩을 사용하고 필요한 경우에만 Fetch Join으로 한 번에 가져오도록 했습니다.

마지막은 아까 말씀드린 RateLimiter인데, SEC API 제한을 지키면서도 최대한 빠르게 데이터를 수집할 수 있게 최적화했습니다."
